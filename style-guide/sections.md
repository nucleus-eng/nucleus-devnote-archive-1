# Sections

## The structure

Every DevNote in the archive follows the same shape. Use it unless there is a reason not to.

1. **Frontmatter** — `title`, `abstract`.
2. **Overview / Introduction** — background, motivation, the system under test. Introduce the main components here, with composition tables if they help.
3. **Composition / Methods** — protocol steps and reaction compositions.
4. **Results** — one subsection per experiment. Each carries: a short paragraph on what was tested and why, a reaction-composition table, the figure or figures, and a paragraph interpreting them.
5. **Conclusions and next steps** — two to four sentences. What was shown, why it matters, what comes next.

**A Discussion section is optional** and earns its place only when findings across several experiments need synthesising. One DevNote in the archive has one; three do not.

**Sections may be dropped, not emptied.** An experiment with no separate base composition jumps from Introduction to the first experimental section, and that is correct. A heading with nothing under it is a stub signal — see [principles](principles.md).

## Composition tables

The archive converged on one six-column form. Use it:

```
Component | Input concentration | Unit | Final concentration | Unit | Volume for one reaction (µL)
```

- Use the `:::{table}` directive with a caption.
- Give it a `:label:`, so it can be referenced with `` {ref}`label` ``.
- Put a totals row last: `| Total volume (µL) | | | | | 40 |`.
- Notes about how a mastermix was used go **inside** the directive body, after the table.

A different schema is correct when the six columns do not fit — the energy-solution table uses five, because its concentrations are tracked through an intermediate solution. Change the columns, not the reader's ability to check the arithmetic.

**Experimental parameter tables are two columns**, `Condition | Description`, and should name every condition including positive and negative controls. That is what makes the design legible without reading the narrative.

## Figures

Two patterns, and the choice is not stylistic.

**Static file** — the figure is a PNG committed in the repo. Reference it by path. Use this when the plot is a committed output artifact.

**Notebook output** — the figure is produced by a notebook cell and referenced as `#fig:name`. Use this when the plot is generated by the analysis, so the figure cannot drift from the data.

:::{danger} `#fig:` references render blank without cell metadata
The `#fig:name` form requires the notebook's output cell to carry a matching `label` in its metadata, or to use the `glue` API. Migrated notebooks that have `display_data` outputs and no `label` render **every** such figure blank, and the page still builds.

Either add `label: fig:name` to each output cell, or use the static-file form. Check the built page, not the source.
:::

**Figures in tab-sets** are the norm for Time Series / End Point pairs. Give every tab-item a `:sync:` key so all tab-sets on the page switch together.

For the MyST mechanics — directive syntax, fence depth, tab-set nesting, cross-reference anchors — use the `author-myst-content` skill. Those rules are not repeated here.

## Notebooks and the narrative

**Notebooks are the computational layer. The narrative interprets, it does not repeat.** Do not paste analysis code into the page.

Notebooks live under `experiments/[YYYYMMDD]-[slug]/` and are listed in the project `toc`. Name them for the experiment: `20250610-ppk-energy-solution-analysis.ipynb`. Never `Untitled.ipynb`.

## Data layout

One dated directory per experiment:

```
experiments/
└── [YYYYMMDD]-[experiment-slug]/
    ├── analysis.ipynb
    ├── [date]-[name]-platemap.csv
    ├── kinetics.png
    └── data/
        ├── [date]-[instrument]-[protocol]-[name]-biotek-cdk.txt
        ├── [date]-[instrument]-[protocol]-[name]-biotek.txt
        └── [date]-[instrument]-[protocol]-[name].xpt
```

Plate-reader runs produce three files from one run — the CDK-parsed text, the raw instrument export, and the XPT binary. **Commit all three.** The parsed file is what the notebook reads; the other two are what lets someone re-parse it when the parser changes.

Platemaps map well positions to conditions and are CSV.
